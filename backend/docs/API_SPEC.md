# OddTrip Backend API 명세 (dev 브랜치 기준)

## 공통 규약

| 항목 | 내용 |
| --- | --- |
| Base URL | 모든 엔드포인트는 `/api` 프리픽스 아래 |
| 응답 래핑 | 성공 시 항상 `{ "data": ..., "error": null }` |
| 에러 응답 | FastAPI 기본 형식 `{ "detail": "메시지" }` (래핑되지 않음). 미처리 예외는 500 `{ "detail": "Internal server error" }` |
| 필드 표기 | 요청/응답 모두 camelCase (`alias_generator=to_camel`, `populate_by_name=True`) |
| 인증 | `Authorization: Bearer <accessToken>` (자체 구현 HS256 JWT). `ALLOW_DEMO_USER_HEADER_AUTH=true`일 때만 `X-User-Id` 헤더 폴백 허용 |
| 액세스 토큰 | 기본 30분 (`AUTH_TOKEN_EXPIRE_MINUTES`), 무상태이므로 폐기 불가 |
| 리프레시 토큰 | 기본 14일 (`REFRESH_TOKEN_EXPIRE_DAYS`), DB에는 SHA-256 해시만 저장, 폐기 가능 |
| 권한 표기 | `-` 비로그인 가능 / `로그인` 인증 필요 / `당사자` 매칭·여행·채팅방 참여자만 / `관리자` role=admin만 |
| 공통 예외 | 401 인증 실패(`Not authenticated` / `User not found` / `Invalid token` / `Token expired`), 403 정지 계정(`이용이 정지된 계정입니다.` — 인증은 됐으나 제재 중), 422 Pydantic 검증 실패 |
| CORS | `CORS_ORIGINS` + 사설망 정규식 허용, `allow_credentials=True` |
| 총 엔드포인트 | HTTP 81개 + WebSocket 1개 (아래 표에 74개 기재, 미기재 7개는 마지막 절 참고) |

## 참고: 알림 발생 지점

알림 행은 원인이 된 상태 변경과 **같은 트랜잭션**에서 INSERT되므로, 롤백된 동작에 대한 알림은 생길 수 없습니다.
WebSocket 푸시는 그 위의 best-effort이며, 오프라인 수신자도 다음 요청에서 행을 그대로 읽습니다.

| type | 발생 API | 받는 사람 | link |
| --- | --- | --- | --- |
| match_request.received | POST /api/match-requests | 수신자 | `/matches?tab=received` |
| match_request.accepted | POST /api/match-requests/{id}/accept | **요청자만** (수락자는 클라이언트가 채팅방으로 바로 이동시킴) | `/chat/{roomId}` |
| match_request.rejected | POST /api/match-requests/{id}/reject | 요청자 | `/matches?tab=sent` |
| match.ended | POST /api/matches/{id}/end | 종료를 호출하지 않은 상대방 | `/matches` |
| trip.created | POST /api/trips | 새 여행을 만들지 않은 동행 | `/my` |
| trip.updated | PATCH /api/trips/{id} | 수정하지 않은 동행 | `/trip/overview` |
| trip.cancelled | DELETE /api/trips/{id} | 취소하지 않은 동행 | `/my` |
| itinerary.approved | PUT /api/trips/{id}/approval/me | 승인한 사람의 동행 | `/trip/schedule` |
| itinerary.change_requested | PUT /api/trips/{id}/approval/me | 수정 요청한 사람의 동행 | `/trip/schedule` |
| itinerary.confirmed | PUT /api/trips/{id}/approval/me | 마지막으로 승인한 사람의 동행 | `/trip/schedule` |

의도적으로 알림을 만들지 않는 경우:

- **요청 취소(cancel)** — 요청자가 자기 요청을 거두는 것이라 알릴 대상이 없음
- **차단(block)** — 차단으로 매칭이 종료돼도 상대에게 알리지 않음. 차단 사실이 노출됨
- **새 메시지** — 채팅 안 읽음 수(`/api/chat/unread-count` + 방별 `unreadCount`)가 이미 같은 사실을 전달. 중복 표시와 알림함 도배를 피함
- **여행 D-1 리마인더** — 스케줄러 미도입으로 보류. 도입 시 같은 테이블에 INSERT하면 됨

> 채팅방 숨기기(`DELETE /api/chat/rooms/{room_id}`)와 매칭 숨기기(`DELETE /api/matches/{match_id}`,
> `DELETE /api/me/matches/{match_id}`)는 호출자에게만 영향을 주므로 WebSocket 이벤트를 보내지 않습니다.

## 참고: 제재

약관 제23조①의 조치 목록을 그대로 유형으로 둡니다. 부과와 해제는 `sanctions`에 쌓이고,
차단 판단에 쓰이는 현재 상태만 `users`에 따로 반영합니다. `get_current_user`가 모든 인증
요청에서 도는 자리라, 여기서 제재 표를 한 번 더 뒤지면 전체 요청에 질의가 하나씩 붙습니다.

| 유형 (`type`) | 기간 | 차단 범위 | 해제 |
| --- | --- | --- | --- |
| warning | 없음 | 없음 (기록만) | 대상 아님 |
| matching_restriction | 필수 | 후보 열람·요청 생성·요청 수락 | 가능 |
| suspension | 필수 | 로그인 + 모든 인증 요청 | 가능 |
| ban | 영구 | 로그인 + 모든 인증 요청 | 가능 |
| withdrawal | 없음 | 계정 종료 (익명화) | 불가 (제24조⑤) |

- **집행 지점** — 로그인은 `POST /api/auth/login`(비밀번호 검증 뒤), 이후 요청은 `get_current_user`, 매칭은 `require_matching_consent`.
- **만료는 스스로 풀립니다.** `suspended_until`/`matching_restricted_until`이 지난 시각이면 판정에서 자동으로 빠지므로 별도 배치가 필요 없습니다.
- **정지는 매칭도 함께 막습니다.** 계정을 못 쓰는데 매칭만 열려 있을 수 없습니다.
- **기간제 제재는 뒤로만 밀립니다.** 짧은 제재를 나중에 부과해 앞선 제재를 실질적으로 푸는 일을 막습니다.
- **관리자 계정은 제재 대상이 아닙니다.** 운영자끼리 서로 잠그면 복구 경로가 서버 접근밖에 남지 않습니다.
- **관리자 지정에는 HTTP 경로가 없습니다.** API로 승격할 수 있으면 그 경로가 곧 권한 상승 통로가 되므로, `.env`의 `ADMIN_EMAIL`/`ADMIN_PASSWORD`로 기동 시 생성하거나 `python -m backend.app.cli promote <email>`로 올립니다. 이미 있는 계정의 비밀번호는 덮어쓰지 않고 권한만 올립니다.
