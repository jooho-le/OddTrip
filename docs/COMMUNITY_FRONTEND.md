# 여행 커뮤니티 프론트 구현

작업 브랜치: `front` · 디자인 기준: 기존 `0562bbe` 기반 OddTrip UI

## 참고와 디자인

- [네이버 블로그 홈](https://section.blog.naver.com/): 실제 브라우저에서 주제별 탐색, 작성자·제목·요약·썸네일 목록, 공감·댓글, 사이드바 구조 확인.
- [네이버 블로그 글쓰기 안내](https://help.naver.com/service/5593/contents/764?lang=ko&osType=MOBILE): 카테고리, 댓글 허용 등 작성 흐름 참고.
- OddTrip의 주황 포인트, 흰 문서형 화면, 얇은 구분선, 기존 헤더와 글꼴 유지. 네이버의 글·이미지·브랜드 자산은 복사하지 않음.
- 예시 글은 화면 검토용으로 작성했으며 사진은 기존 디자인에서 사용하는 Unsplash 분위기 이미지. 실제 작성자·여행 실적을 나타내지 않음.
- `/home`의 기존 매칭 후보·일정 일치 피드는 커뮤니티 추천·최신·현재 여행지 이야기로 교체했다. 매칭은 `/matches`, 내 여행은 `/my`에서 각각 이어간다.

## 화면

| 경로 | 구현 내용 |
| --- | --- |
| `/community` | 여행기·여행 팁·질문·동행 후기, 검색, 최신순·공감순, 페이지 이동, 내 글·저장한 글 |
| `/community/:postId` | 작성자·지역·날짜, 사진·본문·태그, 공감·저장, 댓글 작성·삭제, 내 글 수정·삭제 |
| `/community/write` | 제목·카테고리·지역·본문·태그, 대표 사진 1장, 사진 설명, 댓글 허용, 미리보기·임시저장·작성 완료 |
| `/community/:postId/edit` | 본인이 쓴 글 수정, 수정 중 임시저장, 기존 공감·댓글 유지 |
| `/community/drafts` | 새 글·수정 초안 목록, 이어 쓰기, 초안 삭제 |

기존 일반 사용자 인증과 관리자 전용 라우팅을 유지한다. 데스크톱 헤더와 모바일 하단 메뉴에서 접근한다.

## 동작 범위

- 글·댓글·공감·저장·초안은 모두 서버(`/api/community`)에 저장한다. 다른 회원에게 실제로 보이고 다른 기기에서도 이어 쓸 수 있다. 브라우저 저장 어댑터는 제거했다.
- 차단한 회원과 나를 차단한 회원의 글·댓글은 양쪽 목록에서 빠진다. 목록의 댓글 수도 상세에서 보이는 수와 같다.
- 글·댓글 수정·삭제는 작성자만 할 수 있다. 서버가 거절하면 화면은 그 이유를 그대로 알린다.
- 검색·카테고리·정렬·페이지는 서버 질의로 처리한다. 화면은 한 번에 4건을 받는다.
- 사진은 JPG·PNG·WebP, 800KB 이하 1장이다. 파일 업로드 스토리지는 아직 없어 data URL 문자열을 그대로 저장한다.
- 공유·신고는 아직 서버 기능이 없어 준비 중 안내만 표시한다. 성공 상태를 만들지 않는다.
- 글은 일반 텍스트로 렌더링하며 HTML을 실행하지 않는다. 신규 초안은 계정당 한 개, 수정 초안은 글별 한 개, 여행에서 시작한 초안은 여행별 한 개다.
- 작성 중 돌아가기·링크 이동·새로고침/닫기에는 유실 안내가 있다. 확실히 보관하려면 임시저장을 사용한다.

## 백엔드 계약

게시판 API는 `/api/community`에 구현되어 있다. 아래 표는 화면 동작과 계약의 대응이다.
화면은 아직 브라우저 저장 어댑터를 쓰며, 연결은 `features/community/communityModel.ts`의
로컬 어댑터를 실제 API 어댑터로 바꾸는 작업으로 남아 있다. 예시 자료는 운영 DB에
자동 업로드하지 않는다.

| 화면 동작 | 계약 |
| --- | --- |
| 목록·검색·카테고리·정렬·페이지 이동 | `GET /api/community/posts?category=&q=&view=all\|mine\|saved&sort=latest\|popular&page=&size=` |
| 상세(글·댓글 함께) | `GET /api/community/posts/{postId}` |
| 작성 완료 | `POST /api/community/posts?draftKey=` |
| 수정 완료 | `PUT /api/community/posts/{postId}?draftKey=` |
| 글 삭제 | `DELETE /api/community/posts/{postId}` |
| 공감·저장 | `PUT /api/community/posts/{postId}/like`, `.../save`, 본문 `{"value": true\|false}` |
| 댓글 목록·작성·삭제 | `GET`·`POST /api/community/posts/{postId}/comments`, `DELETE .../comments/{commentId}` |
| 임시저장 목록·저장·삭제 | `GET /api/community/drafts`, `PUT`·`DELETE /api/community/drafts/{draftKey}` |

- 응답은 다른 라우터와 같은 `{ "data": ..., "error": null }` 봉투이고 항목 이름은 camelCase다.
- 제목 1~80자, 본문 10~10,000자, 지역 30자, 태그 각 20자·최대 5개, 댓글 1~1,000자를 화면과 같은 문구로 서버에서도 확인한다.
- 공감·저장은 토글이 아니라 원하는 상태를 보낸다. 같은 요청이 두 번 닿아도 결과가 같다.
- `likeCount`는 내 공감을 포함한 전체이고 `liked`·`saved`·`mine`은 요청한 사람 기준이다.
- 글·댓글 수정·삭제는 작성자만 가능하다. 차단한 상대와 나를 차단한 상대의 글·댓글은 양쪽 목록에서 빠진다.
- 삭제는 행을 지우지 않고 `deleted_at`을 남긴다. 신고·운영 검토에서 원문을 확인할 수 있어야 한다.
- 초안 키는 화면 값을 그대로 쓴다. 새 글 `new`, 수정 초안은 글 id, 여행에서 시작한 글은 `trip:<tripId>`다. 작성·수정 완료 시 `draftKey`를 함께 보내면 그 초안은 같은 요청에서 정리된다.
- `tripId`를 보내면 그 후기가 어느 여행에서 나왔는지 남는다. 글쓴이가 참여한 여행만 연결된다.

### 남은 계약

| 우선순위 | 기능 | 필요한 계약 |
| --- | --- | --- |
| P1 | 사진 | 현재는 화면이 보내는 data URL(JPG·PNG·WebP, 800KB 이하 1장)을 그대로 보관한다. 업로드·스토리지·검사·삭제를 정하면 본문 바이트를 스토리지로 옮기고 행에는 URL만 남긴다. |
| P1 | 신고·운영 | 게시글·댓글 신고 접수와 운영자 검토, 숨김 처리. 화면은 아직 준비 중 안내만 표시한다. |
| P1 | 알림 | 내 글에 댓글이 달렸을 때의 알림과 수신 설정. |
| P2 | 공개 범위 | 비공개·이웃 공개 정책과 권한 없는 글 접근 처리. 현재는 차단 관계를 제외한 회원에게 모두 보인다. |
| P2 | 확장 | 대댓글, 다중 사진, 본문 블록 편집기, 댓글 수정. |

## 검증

- 백엔드 서비스 테스트(`tests/test_community_service.py`) 8건: 작성·수정·삭제와 작성자 제한, 목록 필터·검색·정렬·페이지, 공감 멱등과 저장의 개인 범위, 댓글 허용 설정과 작성자 제한, 차단 양방향, 초안 생애주기, 여행 연결, 입력 한도.
- 프론트 단위 테스트: 입력 검증·태그 파싱(`communityModel.test.ts`), 호출 계약과 응답 매핑(`contracts/frontendApiContracts.test.ts`).
- 실제 Postgres에 붙인 두 계정 왕복 확인: 한 계정이 올린 글을 다른 계정이 목록·상세에서 읽고, 공감이 합산되고, 댓글이 보이고, 저장은 저장한 계정에서만 보이며, 남의 글 수정은 403, 작성 완료 시 초안이 사라지고, 삭제 후 목록에서 빠지는 것까지 확인.
- 타입체크와 프론트 테스트 전체 통과. 브라우저에서 클릭하며 보는 화면 검토는 별도로 필요하다.
