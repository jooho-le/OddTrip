- 기준일: 2026-09-15
- 작업 브랜치: `front`
- 디자인 기준: `0562bbe`
- 프론트 API 계약 기준: `origin/dev@5739957`

## 구현 원칙

- `0562bbe`의 DOM 구조, 타이포그래피, 여행 커버·탭, 문서형 설문, 우측 채팅 드로어를 디자인 원본으로 유지한다.
- 동의, 알림, 관리자, 회원 탈퇴, 2인 조율 기능은 서버 응답을 성공의 기준으로 사용한다.
- 저장 API가 없는 기능은 `현재 준비 중인 기능입니다.` 팝업만 표시하고 완료·저장 상태를 만들지 않는다.
- 예시 데이터는 화면 진입 시 세션당 한 번 팝업으로 알린다. 화면에 상시 `DEMO` 배지를 표시하지 않는다.
- 이 문서의 Backend Todo는 프론트가 기다리는 계약을 정리한 것이며, `front` 작업에서 백엔드 코드를 수정하지 않는다.

## 완료된 프론트 연결

### 가입·기능별 동의

- 영향 화면: `/auth`, `/legal/*`, `/matches`, `/settings`
- 반영 내용: 가입 필수 4종과 마케팅 선택 여부를 가입 payload에 포함한다. 브라우저 전용 동의 저장소는 제거했다. 매칭 프로필·안전수칙 동의 게이트, 동의 조회·이력, 마케팅 철회를 연결했다.
- 서버 계약: `POST /api/auth/register`, `GET/POST /api/me/consents`, `GET /api/me/consents/history`
- 우선순위: 완료
- 검증 조건: 필수 동의가 빠진 가입은 전송하지 않고, 선택 동의 거부도 명시적으로 전송한다. 새로고침 후 동의 상태는 서버에서 복원한다.

### 제품 알림

- 영향 화면: 전역 헤더, 홈, 매칭 요청, 신고·제재 결과
- 반영 내용: 목록·안 읽음 수·개별/전체 읽음을 연결했다. 기존 채팅 WebSocket에서 `notification.created`를 받아 서버 ID로 중복 제거한다.
- 서버 계약: `GET /api/notifications`, `GET /api/notifications/unread-count`, `PUT /api/notifications/read`, WebSocket `notification.created`
- 우선순위: 완료
- 검증 조건: 재연결·중복 이벤트로 동일 알림이 두 번 추가되지 않고 읽음 상태와 badge가 서버 응답에 맞는다. UI 안내 팝업은 제품 알림 상태를 바꾸지 않는다.

### 관리자 회원·여행·신고

- 영향 화면: `/admin`, `/admin/users`, `/admin/trips`, `/admin/trips/:id`, `/admin/reports`
- 반영 내용: 통계, 회원 상세·동의 상태·제재 이력, 제재 부과/해제, 여행 목록·상세, 신고 목록·상세·검토를 실제 API에 연결했다. 검색·상태 필터·서버 페이지네이션·로딩·빈 결과·오류·재시도를 제공한다. 운영자 로그인은 `/admin`으로 바로 이동하며 일반 회원용 보호 화면 진입도 관리 콘솔로 되돌린다.
- 서버 계약: `/api/admin/stats`, `/api/admin/users*`, `/api/admin/trips*`, `/api/admin/reports*`, `/api/admin/sanctions*`
- 우선순위: 완료
- 검증 조건: `role === "admin"`만 화면에 진입하며 일반 계정의 권한을 프론트에서 생성·변경하지 않는다. 제재·신고 결과는 서버 응답 후에만 갱신한다.

### 홈 기록·일정 일치·장소 성향 보기

- 영향 화면: `/home`, `/trip/places`
- 반영 내용: 홈의 최근 기록은 `GET /api/trips` 결과를 최신 순으로 보여준다. 일정 일치는 현재 여행 기간과 받은/보낸 활성 동행 요청의 기간을 비교하며, 현재 여행 날짜가 없으면 다가오는 요청을 보여준다. 장소의 내 성향·동행 성향·반대 성향 체험은 저장된 개인 선호, 두 사람의 TTI와 추천 장소의 태그·속성을 이용해 현재 결과를 클라이언트에서 정렬·필터링한다.
- 서버 계약: `GET /api/trips`, `GET /api/match-requests/received`, `GET /api/match-requests/sent`, `/api/trips/{tripId}/preferences/pair`, 기존 관광지 응답
- 우선순위: 완료
- 검증 조건: 파생 보기는 서버 원본을 변경하지 않고, 중복 요청을 한 번만 표시하며, 현재 여행 기간과의 경계 날짜도 겹침으로 계산한다. 선호나 TTI 신호가 없으면 임의 결과 대신 빈 상태와 작성 안내를 표시한다.

### 개인 선호·양쪽 제출 상태·합의안

- 영향 화면: `/survey/preference`, `/trip/coordination`
- 반영 내용: 내 선호 저장, 양쪽 제출 상태·비교, 합의안 제안·수락·거절을 연결하고 `preference.updated`, `preference.proposal_created`, `preference.proposal_responded` 실시간 이벤트로 갱신한다.
- 서버 계약: `/api/trips/{tripId}/preferences/me`, `/preferences/pair`, `/preferences/proposals*`
- 우선순위: 완료
- 검증 조건: 두 사용자 상태를 구분하고 상대가 제출하기 전에 상대 답안을 노출하지 않는다. 제안 응답 후 양쪽 화면이 동일 상태로 갱신된다.

### 세션·회원 탈퇴·채팅 드로어

- 영향 화면: 전체 보호 화면, `/settings`, `/chat`, `/chat/:roomId`
- 반영 내용: access token 401 시 refresh 후 원 요청을 재시도하고 실패 시 세션을 지운 뒤 로그인으로 이동한다. 회원 탈퇴를 서버에 연결했다. 채팅방 URL은 직접 접근하거나 앱에서 열어도 우측 드로어로 표시한다.
- 서버 계약: `POST /api/auth/refresh`, `POST /api/auth/logout`, `POST /api/users/me/withdraw`, `/api/chat/*`
- 우선순위: 완료
- 검증 조건: 동시에 발생한 401은 refresh 요청을 공유하고, refresh 실패 계정은 보호 화면에 남지 않는다. 채팅 URL과 닫기 경로가 새로고침 후에도 유효하다.

## 백엔드 계약 대기

아래 항목은 프론트 화면과 진입 경로까지 구현했다. 서버 계약이 생기기 전에는 입력값을 서버에 저장하지 않으며, 실행 버튼은 공통 `현재 준비 중인 기능입니다.` 팝업만 연다.

### P0 · Trip 생성·수정·삭제

- 영향 화면: 홈, 내 여행, 여행 개요
- 현재 제한: `/trips/new`, `/trip/settings`에 문서형 입력 화면과 필수값·날짜 순서·30일 상한 검증은 구현했다. 여행은 여전히 매칭 수락 시 자동 생성되며 직접 생성·수정·삭제는 저장하지 않는다.
- 필요한 백엔드 계약: Trip CRUD endpoint, 두 참가자의 수정 권한, 기간 30일 검증, 삭제/종료 정책, 낙관적 잠금용 version.
- 우선순위: P0
- 검증 조건: 권한 없는 사용자는 403, 오래된 version은 409가 되며 생성·수정 결과가 두 사용자 여행 목록에 동일하게 보인다.

### P0 · 일정 버전·양쪽 승인

- 영향 화면: `/trip/schedule`, `/survey/approval`
- 현재 제한: 일정 조회·생성·재생성은 가능하다. `/survey/approval`에 버전·참여자별 상태·승인/수정요청 문서를 구현했지만 해당 결정을 저장할 수 없다. 일정 항목별 검토 드로어도 수정 메모를 저장하지 않는다.
- 필요한 백엔드 계약: 일정 `version`/`generatedAt`/입력 snapshot, 사용자별 승인 endpoint, 수정 요청 endpoint, 재생성 시 이전 승인 무효화 규칙.
- 우선순위: P0
- 검증 조건: 두 사용자가 같은 최신 version을 승인해야 완료되며 재생성 후 과거 승인은 완료 계산에서 제외된다.

### P1 · 휴대전화 본인인증

- 영향 화면: 가입, 프로필, 매칭 상세, 동행 요청
- 현재 제한: `/verification`에 전화번호 입력, 인증번호, 완료 단계의 화면 구조와 입력 검증을 구현했다. 요청/검증 endpoint가 없어 어떤 단계에서도 발송·인증 성공으로 전환하지 않는다.
- 필요한 백엔드 계약: 인증 요청·검증·재시도·만료 endpoint, provider reference, 성인/본인확인 최소 공개 상태, 감사·파기 정책.
- 우선순위: P1
- 검증 조건: 테스트 코드는 운영에서 거절되고 인증 전 제한은 서버에서도 강제되며 상대에게 원문 식별정보가 노출되지 않는다.

### P1 · 여행 D-1 알림

- 영향 화면: 알림함, 홈, 여행 개요
- 현재 제한: 일반 알림함은 연결됐고 `/settings/notifications`에 D-1 채널 상태를 표시한다. 여행 시작일 기준 예약 작업이 없어 D-1 이벤트가 생성되지 않으며 토글도 저장하지 않는다.
- 필요한 백엔드 계약: timezone을 포함한 예약 스케줄러, 알림 생성 idempotency key, 취소·기간 변경 재계산, 실패 재시도.
- 우선순위: P1
- 검증 조건: 여행당 사용자별 한 번만 생성되고 기간 변경·취소 시 잘못된 알림이 발송되지 않는다.

### P1 · 모바일 Push

- 영향 화면: 모바일 앱, 알림 설정, 백그라운드 상태
- 현재 제한: `/settings/notifications`에서 인앱 알림과 실제 마케팅 동의는 서버 상태로 표시한다. 모바일 Push 행은 계약 대기 상태이며 앱이 닫힌 상태의 푸시를 제공하지 않는다.
- 필요한 백엔드 계약: 기기 토큰 등록·철회, 사용자별 수신 설정, APNs/FCM 전송 결과, deep link allowlist, 토큰 정리.
- 우선순위: P1
- 검증 조건: 로그아웃·철회된 기기로 전송하지 않고 같은 알림 ID가 인앱·푸시에 중복 생성되지 않으며 deep link가 허용 경로만 연다.

### P1 · 장소 개인 투표와 개인 북마크

- 영향 화면: `/trip/places`, 내 여행
- 현재 제한: 여행 단위 저장·제외는 서버에 반영한다. 장소 상세의 개인 투표 다이얼로그는 원하는 곳/괜찮음/건너뜀 입력 구조만 제공하며 제출해도 로컬·서버 집계를 변경하지 않는다. 여행 밖 개인 북마크도 아직 구분할 수 없다.
- 필요한 백엔드 계약: `/votes/me`, 개인 bookmark endpoint, 집계와 일정 생성에 사용한 vote snapshot.
- 우선순위: P1
- 검증 조건: 두 사용자 표가 분리되고 개인 북마크가 상대의 여행 선택을 바꾸지 않으며 일정은 명시된 snapshot을 사용한다.

### P2 · 관리자 정적 영역

- 영향 화면: `/admin/attractions`, `/admin/tti`, `/admin/operations`
- 현재 제한: 관광지 예시 목록의 검색·분류·상세 열람은 프론트에서 동작하고 TTI 질문 목록·축 필터는 기존 실제 질문 API를 사용한다. 관광지 추가·편집, TTI 요약 수치·버전·문항 편집, 실시간 운영 상태 관리 API는 없다. 세션당 한 번 예시 데이터의 범위를 안내하고 저장 조작은 준비 중 팝업만 연다.
- 필요한 백엔드 계약: 관리자 관광지/TTI CRUD, 배포 버전, 외부 연동 health/latency/checkedAt, 감사 로그와 서버 권한 강제.
- 우선순위: P2
- 검증 조건: 모든 수치에 실제 조회 시각과 출처가 있고 일반 사용자는 endpoint에서 403을 받으며 변경 이력이 감사 로그에 남는다.

## 프론트 후속 작업

### P2 · Responsive·Capacitor

- 영향 화면: 전체, 채팅 드로어, 문서형 설문, 관리자 표
- 현재 제한: 1024px·390px 수평 오버플로 방지까지 검증하며 모바일 전용 IA, 가상 키보드, 안전영역과 실제 기기 검증은 별도다.
- 필요한 작업: safe-area, 키보드 resize, 드로어 우선 뒤로가기, 44px 터치 타깃, iOS/Android 기기 matrix.
- 우선순위: P2
- 검증 조건: 키보드가 입력을 가리지 않고 뒤로가기가 드로어를 먼저 닫으며 대표 기기에서 핵심 흐름을 완료한다.

### P2 · Release 준비

- 영향 화면: 전체 서비스와 릴리스 운영
- 현재 제한: 외부 이미지·폰트 자산, 법적 문서의 시행일·운영주체, preview/CI/배포 설정이 최종 확정되지 않았다.
- 필요한 작업: 자산 권리·고정 버전, 법률 검토 문서, 환경변수 검증, CI build/test, preview smoke, CSP/CORS와 rollback.
- 우선순위: P2
- 검증 조건: 깨끗한 checkout에서 테스트·빌드가 재현되고 외부 네트워크 실패에도 핵심 레이아웃이 유지되며 preview와 rollback 점검을 통과한다.

### P2 · 지도 SDK와 접근성 완성

- 영향 화면: `/trip/schedule/map`, 장소 상세 다이얼로그, 일정 항목 검토 드로어
- 현재 제한: 경로 문서는 실제 일정 데이터와 좌표 가용성을 보여주지만 지도 SDK·길찾기 요청을 실행하지 않는다. 다이얼로그/드로어의 기본 키보드 닫기는 제공하되 실제 기기 스크린리더 검증은 남아 있다.
- 필요한 작업: 지도 공급자·키·이용약관 확정, 좌표 없는 장소 fallback, 경로 실패/쿼터 초과 상태, 초점 고정과 복귀, 스크린리더 레이블·실기기 테스트.
- 우선순위: P2
- 검증 조건: 지도 키가 없는 환경에서도 일정 내용을 읽을 수 있고, 모든 오버레이가 키보드와 스크린리더로 열기·탐색·닫기 가능하며 호출 실패가 일정 데이터를 훼손하지 않는다.
