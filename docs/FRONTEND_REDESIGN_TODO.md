## 1차 구현 경계

- 이번 1차는 첨부 HTML의 시각 언어와 정보 구조를 React에 이식하고, 현재 브랜치에 이미 존재하는 API만 연결한다.
- 활성 사용자 경로는 `useTripStore`, `useMatchRequestStore`, `useChatStore`를 사용하며 기존 `useProtoStore`와 정적 알림 스토어는 제거했다.
- `backend/`, Alembic migration, 루트 `tests/`는 변경하지 않는다.
- 저장 API가 없는 기능은 가능한 범위만 화면에서 체험하게 하고, 진입 시 별도 안내 팝업으로 저장되지 않음을 알린다.
- 실제로 수행할 수 없는 동작은 버튼 클릭 시 `현재 준비 중인 기능입니다.` 팝업을 표시하며 성공 상태를 만들지 않는다.
- 이 팝업은 제품의 알림 기능과 분리된 UI 안내이며, 화면에 `DEMO` 배지를 상시 노출하지 않는다.
- `775ed47`은 이번 브랜치에 반영하지 않는다. 계약 차이는 아래 P0 Sync에서 별도로 처리한다.

## P0 Backend

### 개인별 조율 제출

- 영향 화면: `/decision/select`, `/decision/waiting`, `/decision/concession`
- 현재 제한: 여행 단위의 공동 `preferences_json`만 저장할 수 있다. 사용자별 원본 답안, 비공개 여부, 제출 시각, 상대 제출 상태를 구분할 수 없다.
- 필요한 백엔드 계약:
  - `POST/PUT /api/trips/{tripId}/coordination/submissions/me`
  - 사용자별 draft/submitted 상태와 `submittedAt`
  - 제출 전 비공개 보장 및 양쪽 제출 후 공개 가능한 집계 응답
  - 중복 제출에 안전한 idempotency key 또는 version
- 우선순위: P0
- 검증 조건:
  - 두 사용자 세션에서 서로의 원본 답안은 양쪽 제출 전 조회되지 않는다.
  - 새로고침과 다른 기기 로그인 후에도 내 draft/submitted 상태가 복원된다.
  - 한 사용자의 제출을 상대 제출로 오인하지 않는다.

### Odd Rule 합의

- 영향 화면: `/decision/odd-rule`, `/proposal`
- 현재 제한: 규칙을 화면에서 비교할 수만 있고, 양쪽 선택·합의·철회 상태를 저장하지 않는다.
- 필요한 백엔드 계약:
  - `GET /api/trips/{tripId}/odd-rule`
  - `PUT /api/trips/{tripId}/odd-rule/me`
  - 양쪽 선택 결과, 합의된 rule ID, 합의 버전, 확정·철회 시각
  - 동시에 다른 규칙을 고른 경우의 conflict 응답
- 우선순위: P0
- 검증 조건:
  - 양쪽이 같은 규칙을 선택하기 전에는 합의 완료로 표시되지 않는다.
  - 한쪽 철회 또는 변경 시 기존 확정 상태가 무효화된다.
  - 최신 버전이 아닌 요청은 409 등 명시적 충돌로 거절된다.

### 조율안 투표·확정

- 영향 화면: `/proposal`, `/proposal/compare`, `/proposal/:variantId`
- 현재 제한: 현재 관광지 목록을 프론트에서 재정렬한 세 가지 `DEMO LOGIC`만 열람한다. 독립 생성안, 영속 ID, 사용자별 투표, 최종 확정 상태가 없다.
- 필요한 백엔드 계약:
  - `POST /api/trips/{tripId}/proposals/generate`
  - `GET /api/trips/{tripId}/proposals`
  - `PUT /api/trips/{tripId}/proposals/{proposalId}/votes/me`
  - `POST /api/trips/{tripId}/proposals/{proposalId}/confirm`
  - 생성 근거, 입력 snapshot/version, 양쪽 반영 점수의 산출 근거
- 우선순위: P0
- 검증 조건:
  - 세 안이 서로 다른 영속 proposal ID와 동일 입력 version을 가진다.
  - 한쪽 투표만으로 확정되지 않는다.
  - 확정 후 장소·일정 단계가 같은 proposal version을 참조한다.

### 일정 버전·양쪽 승인 API

- 영향 화면: `/itinerary`, `/itinerary/:id`, `/approval`
- 현재 제한: 일정 생성·재생성은 가능하지만 버전, 승인자, 수정 요청, 재승인 상태를 저장할 수 없다.
- 필요한 백엔드 계약:
  - 일정 응답의 `version`, `generatedAt`, `sourceSnapshot`
  - `POST /api/trips/{tripId}/itinerary/{version}/approvals/me`
  - `POST /api/trips/{tripId}/itinerary/{version}/revision-requests`
  - 사용자별 승인 상태와 최신 일정 생성 시 이전 승인 무효화 규칙
- 우선순위: P0
- 검증 조건:
  - 두 사용자 모두 같은 최신 version을 승인해야만 완료된다.
  - 일정 재생성 후 이전 version의 승인은 완료 계산에 포함되지 않는다.
  - 수정 요청 내용과 처리 상태가 양쪽 세션에서 동일하게 보인다.

## P0 Sync

### `775ed47` 매칭·채팅 계약 반영

- 영향 화면: `/matches`, `/chat`, `/chat/:roomId`, 실시간 안 읽음 상태
- 현재 제한: 이번 1차는 기준 커밋의 `room.created` 이벤트와 `DELETE /api/matches/{matchId}` 계약을 유지한다. `775ed47`의 백엔드·테스트 변경은 의도적으로 포함하지 않았다.
- 필요한 반영:
  - WebSocket 이벤트를 `room.created`에서 `chat.room_created`로 전환
  - room-created payload의 `userIds` 계약 반영
  - 숨김 경로를 `DELETE /api/me/matches/{matchId}`로 전환
  - 추가된 매칭·채팅 응답 필드의 프론트 타입 동기화
  - 이벤트 전환 기간이 필요하면 구·신 이벤트를 함께 받는 호환 창 정의
- 우선순위: P0
- 검증 조건:
  - 요청 수락 직후 양쪽 클라이언트가 새 채팅방을 중복 없이 한 번만 추가한다.
  - 재연결 후 방 목록·안 읽음 수가 서버와 일치한다.
  - 숨김 요청이 다른 사용자의 매칭을 삭제하지 않는다.
  - `775ed47` 반영 후 백엔드 전체 테스트와 프론트 계약 테스트가 함께 통과한다.

## P1 Safety

### 본인인증

- 영향 화면: 회원가입, 동행 요청서, 매칭 상세, 프로필
- 현재 제한: 현재 계정 인증은 이메일·비밀번호뿐이며 동행 신원 확인 상태를 표시할 서버 계약이 없다.
- 필요한 백엔드 계약: 인증 요청/상태/만료/재시도 endpoint, 검증 provider reference, 최소 공개 상태, 민감 데이터 보존·삭제 정책.
- 우선순위: P1
- 검증 조건: 인증하지 않은 사용자의 제한이 서버에서도 강제되고, 상대에게 원문 신분 정보가 노출되지 않는다.

### 서버 알림

- 영향 화면: 헤더 알림, 홈 최근 알림, 매칭 요청, 조율, 일정, 안전 정보
- 현재 제한: 채팅 안 읽음 수만 실시간 API 값이다. 여행 단계나 날씨 알림을 임의 생성하지 않는다.
- 필요한 백엔드 계약: 알림 목록·읽음 처리·cursor pagination, 알림 종류와 대상 route, WebSocket/push 이벤트 ID, 중복 제거 키.
- 우선순위: P1
- 검증 조건: 같은 이벤트가 재연결·재시도 때 중복 표시되지 않고, 읽음 상태가 기기 간 동기화된다.

### 후기

- 영향 화면: 완료 여행, 내 여행 아카이브, 동행 프로필
- 현재 제한: 여행 완료 후 후기 작성·조회·공개 범위 기능이 없다.
- 필요한 백엔드 계약: 여행 참가자 검증, 후기 생성·수정·숨김, 공개 범위, 상호 공개 시점.
- 우선순위: P1
- 검증 조건: 참가하지 않은 사용자는 후기를 작성할 수 없고, 차단·신고 상태에 따른 노출 규칙이 적용된다.

### 신고·차단 후속 처리

- 영향 화면: 채팅 드로어, 동행 상세, 매칭·여행 기록
- 현재 제한: 신고·차단 요청 endpoint는 있으나 접수 후 상태, 이의 제기, 운영 처리 결과를 확인할 사용자 흐름이 없다.
- 필요한 백엔드 계약: 내 신고 목록·상태, 차단 목록, 해제 정책, 신고 처리 결과와 안전한 메시지.
- 우선순위: P1
- 검증 조건: 차단 직후 채팅·매칭 접근이 서버에서 차단되고, 신고 세부 정보가 피신고자에게 노출되지 않는다.

## P1 Sharing

### 일정 공유·공개 링크

- 영향 화면: `/itinerary`, 완료 여행
- 현재 제한: 공유 버튼은 준비 중 안내 팝업만 열며 URL을 만들거나 공유 성공 상태로 바꾸지 않는다.
- 필요한 백엔드 계약: scope가 제한된 share token, 만료·철회, 공개 필드 allowlist, 조회 감사 정보.
- 우선순위: P1
- 검증 조건: 철회·만료된 링크는 접근할 수 없고, 채팅·개인 조율 데이터가 공개 응답에 포함되지 않는다.

### 실시간 위치

- 영향 화면: 일정 상세, 안전 정보, 여행 중 공유 화면
- 현재 제한: 위치 수집·공유 상태와 동의 철회 기능이 없다.
- 필요한 백엔드 계약: 명시적 opt-in, TTL이 있는 위치 업데이트, 상대 조회 권한, 즉시 중지·삭제, 마지막 갱신 시각.
- 우선순위: P1
- 검증 조건: 동의 전에는 위치가 전송되지 않고, 공유 중지 후 새 조회와 WebSocket 전송이 즉시 막힌다.

### 재난 정보 갱신

- 영향 화면: `/safety`, 일정 우측 안전 카드, 헤더 알림
- 현재 제한: 안전 응답에 외부 출처·원문 ID·갱신 시각이 없으면 `출처 미제공`으로 표시한다.
- 필요한 백엔드 계약: 기관명, source ID/URL, issuedAt/updatedAt/expiresAt, 여행 지역 연관성, stale 여부.
- 우선순위: P1
- 검증 조건: 만료 정보는 현재 특보로 표시되지 않고, 동일 source ID의 갱신은 중복 카드가 아닌 업데이트로 처리된다.

## P1 Data

### 개인 저장 장소

- 영향 화면: `/attractions`, `/attractions/:id`, 내 여행
- 현재 제한: 저장·제외는 여행 단위 상태이므로 누가 저장했는지와 개인 북마크를 구분하지 못한다.
- 필요한 백엔드 계약: 사용자 개인 bookmark endpoint와 여행별 selection을 분리한 응답.
- 우선순위: P1
- 검증 조건: 개인 북마크는 다른 동행의 여행 선택을 바꾸지 않고, 계정의 여러 여행에서도 복원된다.

### 여행별 장소 투표

- 영향 화면: 추천 여행지 카드, 장소 상세, 일정 생성 입력
- 현재 제한: 사용자별 찬반·보류 투표와 양쪽 결과가 없다. 투표 동작은 준비 중 안내 팝업만 열고 상태를 바꾸지 않는다.
- 필요한 백엔드 계약: `PUT /api/trips/{tripId}/attractions/{id}/votes/me`, 사용자별 vote, 집계, 변경 시각, 일정 생성에 사용된 vote snapshot.
- 우선순위: P1
- 검증 조건: 두 사용자 표가 분리 저장되고, 일정은 명시된 vote snapshot만 사용한다.

## P2 Admin

### 정적 관리자 데이터를 실제 API로 교체

- 영향 화면: `/admin/*`
- 현재 제한: 관리자 페이지 수치·목록·운영 상태는 모두 정적이다. 관리자 진입 시 별도 체험 안내 팝업으로 한 번 고지한다.

- 검증 조건: 일반 사용자는 모든 관리자 endpoint에서 403을 받고, 화면 수치가 API 응답 및 조회 시각과 일치한다.

### 배포·CI 준비

- 영향 화면: 전체 서비스와 릴리스 운영
- 현재 제한: 이번 작업은 로컬 구현·검증만 수행하며 원격 push, 배포, 환경별 secret 설정을 하지 않는다.
- 필요한 작업: CI build/test, preview 환경, CSP/CORS, 환경변수 검증, bundle·접근성 budget, rollback 절차.
- 우선순위: P2
- 검증 조건: 깨끗한 checkout에서 프론트 테스트·빌드·백엔드 테스트가 재현되고, preview smoke 및 rollback rehearsal가 통과한다.
